# shooking 쇼핑몰 프로젝트

작성자: hyeon (개인 프로젝트)

## 1. 프로젝트 개요

### 1.1 프로젝트 소개

shooking은 20~30대를 타깃으로 한 패션 브랜드로,  
주력 상품은 신발입니다.

본 프로젝트는 shooking 브랜드의 쇼핑몰 웹사이트를 구현하는 것으로,  
상품 탐색부터 장바구니, 결제까지 이어지는 전체 구매 흐름을 구성하는 것을 목표로 합니다.

특히 주요 사용자층의 스마트폰 이용 비중을 고려하여 모바일 퍼스트 설계(Mobile-First Design)를 적용했으며,  
모바일 환경에 최적화된 구조를 중심으로 사용자 경험을 설계했습니다.

또한 이미지 중심의 UI를 통해 직관적인 상품 탐색 경험을 제공하는 데 중점을 두었습니다.

### 1.2 프로젝트 목적

- 이미지 중심의 직관적인 상품 탐색 경험 제공
- 상품 탐색 → 장바구니 → 결제로 이어지는 자연스러운 사용자 흐름 구성
- 모바일 환경에 최적화된 UI/UX 구현
- 결제 수단 등록 및 선택 기능을 포함한 결제 경험 제공

### 1.3 프로젝트 범위

#### 현재 구현 범위

- 상품 목록 페이지
- 상품 상세 페이지
- 장바구니 페이지 (상품 조회, 추가, 삭제, 수량 변경)
- 결제 수단 선택 페이지
- 카드 등록 페이지
- 페이지 간 라우팅 연결

#### 진행 중 / 예정 기능

- 보유 카드 및 결제 상태 관리
- 결제 대상 장바구니 데이터 연동
- 결제 완료 데이터 처리 및 상태 관리
- 결제 완료 페이지 접근 제어

### 1.4 프로젝트 특징

- 모바일 퍼스트 기반 UI 설계 및 반응형 대응
- 상태 기반 장바구니 및 결제 흐름 구성
- 컴포넌트 단위 재사용 구조
- 테스트 점진적 도입

## 2. 시스템 아키텍처

### 2.1 기술 스택 구성

본 프로젝트는 React 기반 SPA 구조로,  
라우팅, 상태 관리, UI 개발, 테스트 환경을 역할별로 분리하여 구성했습니다.

#### Frontend

- React 18 (Vite 기반)
- JavaScript (ES6+)
- Tailwind CSS

> 컴포넌트 기반 UI 구성 및 모바일 퍼스트 스타일링 적용

#### Routing

- React Router v7

> 페이지 간 이동 및 사용자 흐름 관리  
> (상품 → 장바구니 → 결제)

#### State Management

- Recoil

> 장바구니 및 결제 관련 전역 상태 관리  
> atom 및 selector 기반 파생 상태 구조

#### UI Development

- Storybook

> 컴포넌트 단위 UI 개발 및 문서화

#### Testing

- Vitest
- React Testing Library
- Cypress (예정)

> 단위 테스트 및 사용자 흐름 기반 E2E 테스트

#### Deployment

- GitHub Actions (CI/CD)
- GitHub Pages

> GitHub Actions를 통해 빌드 및 배포를 자동화하고,  
> 빌드 결과물(dist)을 GitHub Pages에 배포하는 구조로 구성했습니다.

### 2.2 전체 구조 개요

본 프로젝트는 React 기반 SPA 구조로 구성되어 있습니다.

페이지 간 이동은 React Router로 관리하며,  
장바구니 및 결제 관련 전역 상태는 Recoil을 중심으로 구성했습니다.

UI는 컴포넌트 단위로 분리하고,  
테스트와 문서화는 각각 Vitest/Cypress, Storybook을 기준으로 운영합니다.

데이터 흐름은 사용자 액션을 기반으로 상태를 업데이트하고  
UI를 재렌더링하는 구조로 구성되어 있습니다.

### 2.3 페이지 흐름 구조

```text
상품 목록 (/)
 ├── 상품 상세 (/products/:id)
 │    ├── 장바구니 담기 → 장바구니 (/cart)
 │    └── 바로 구매 → 결제 (/payments) (예정)
 ├── 장바구니 아이콘 클릭 → 장바구니 (/cart)
 └── 담기 버튼 클릭 → 장바구니 상태 업데이트

장바구니 (/cart)
 └── 결제하기 → 결제 (/payments)

결제 (/payments)
 ├── 카드 선택
 ├── 카드 추가 → 카드 등록 (/payments/new)
 └── 결제 완료 → 결제 완료 (/payments/success)
```

> 사용자 흐름 기준: 상품 탐색 → 장바구니 → 결제 → 완료

#### 결제 상태

현재 결제 관련 상태는 보유 카드 목록, 선택 카드, 결제 대상 상품 정보를 중심으로 구성하고 있으며,

### 2.6 데이터 흐름

```text
사용자 액션 → Recoil 상태 업데이트 → selector 기반 파생 상태 계산 → UI 재렌더링
```

> 상태 변경에 따라 UI가 갱신되는 구조로, 장바구니 개수, 금액, 결제 관련 정보가 화면에 반영됩니다.

## 4. 개발 규칙

### 4.1 브랜치 전략

본 프로젝트는 다음과 같은 브랜치 전략을 사용합니다.

- `main`: 최종 배포 기준 브랜치
- `dev`: 개발 통합 브랜치
- `feature/*`: 기능 개발 브랜치
- `fix/*`: 버그 수정 브랜치
- `chore/*`: 라이브러리 설정 및 개발 환경 관련 작업 브랜치
- `hotfix/*`: 운영 중 긴급 수정이 필요한 경우 사용하는 브랜치

> 긴급 이슈 발생 시 `hotfix/*` 브랜치에서 수정 후 `main` 브랜치에 우선 반영하고, 이후 `dev` 브랜치에도 동기화

#### 브랜치 흐름

1. 기능 개발은 `feature/*` 브랜치에서 진행
2. 작업 완료 후 `dev` 브랜치로 병합
3. `dev` 브랜치에서 통합 테스트 및 동작 확인
4. 최종 배포 시 `main` 브랜치로 병합

> 현재 `dev` 브랜치를 기준으로 GitHub Actions를 활용한 빌드 및 배포 자동화(CI/CD)를 구성하고 있으며,  
> GitHub Pages를 통해 정적 웹 애플리케이션을 배포하고 있습니다.  
> 향후 `main` 브랜치를 기준으로 배포를 진행할 예정이며,  
> Vercel 또는 AWS 기반 배포 환경으로도 확장할 예정입니다.

### 4.2 커밋 메시지 규칙

커밋 메시지는 변경 내용을 명확하게 전달하기 위해 다음 규칙을 따릅니다.

- prefix는 영어로 작성 (`feat`, `fix`, `refactor`, `style`, `chore`, `test`, `docs`)
- 제목 및 메시지 본문은 한글로 작성
- scope 및 이모지는 사용하지 않음
- 하나의 커밋은 하나의 변경 사항을 기준으로 작성하되,  
  관련된 수정(예: UI 수정 + 테스트 추가)은 하나의 커밋으로 묶을 수 있음
- 변경 사항 중심으로 간결하게 작성
- 모호한 표현 지양

#### prefix 설명

각 prefix는 변경 목적에 따라 다음과 같이 구분하여 사용합니다.

- `feat`: 새로운 기능 추가 (컴포넌트, 페이지, 로직 포함)
- `fix`: 버그 수정 및 기존 기능 수정 (오타, 오류 포함)
- `refactor`: 기능 변경 없이 코드 구조 개선 (파일 이동, 로직 분리 포함)
- `style`: 코드 포맷팅 및 UI 스타일 변경 (동작 영향 없음)
- `chore`: 설정, 빌드, 패키지 및 환경 관련 작업
- `test`: 테스트 코드 추가 및 수정
- `docs`: 문서 작성 및 수정

#### 본문 작성 기준

- 복잡한 변경이거나 여러 작업이 포함된 경우 작성
- 변경 이유 또는 의도를 간단히 설명
- 선택 사항이지만, 협업 시 가독성을 위해 작성 권장

#### 예시

- `feat: ShippingFee 컴포넌트 구현 및 스토리, 테스트 추가`
- `fix: React 18로 다운그레이드하여 Recoil 호환성 이슈 해결`
- `fix: 배송비 무료 문구 표시 조건 반영 및 관련 문서와 테스트 수정`
- `refactor: useCartActions를 useSetRecoilState 기반으로 개선`
- `style: 아이콘 교체 및 장바구니 UI 디테일 수정`
- `chore: simple-import-sort 설정 추가 및 설정 파일 정리`
- `test: CartItem 삭제 버튼 동작 테스트 추가`
- `docs: 장바구니 페이지 구조 및 테스트 범위 문서 추가`

### 4.3 코딩 스타일 가이드

프로젝트 전반의 코드 일관성과 유지보수성을 위해 다음 기준을 따릅니다.

#### 네이밍 규칙

- 컴포넌트: PascalCase (`CartItem`, `OrderSummary`)
- 변수 및 함수: camelCase (`handleSubmit`, `cartItems`)
  - 함수명은 역할이 드러나도록 명확하게 작성
  - 이벤트 핸들러 함수는 `handle` prefix를 사용 (`handleClick`, `handleSubmit`)
  - 상태 변경 함수는 `set` prefix를 사용 (`setCartItems`, `setIsOpen`)
  - 비즈니스 로직 함수는 동사 기반으로 작성 (`addToCart`, `removeCartItem`)
  - 계산 및 파생 로직 함수는 의미를 명확히 드러내도록 작성 (`calculateTotalPrice`, `formatPrice`)
  - boolean 반환 함수는 `is`, `has`, `can` prefix를 사용 (`isCartEmpty`, `hasItems`, `canSubmit`)
- 커스텀 훅: camelCase + `use` prefix (`useCart`, `usePayments`)
- 파일명:
  - 컴포넌트(페이지 컴포넌트 포함): PascalCase (`CartItem.jsx`, `MyCardsPage.jsx`)
  - 훅 / 유틸 함수: camelCase (`useCart.js`, `formatPrice.js`)
- 폴더명:
  - 소문자 사용
  - 단어가 길어질 경우 kebab-case로 구분 (`select-card`, `register-card`)

#### 폴더 구조

- 기능 단위(feature-based)로 폴더를 분리하여 구성
- 페이지, 컴포넌트, 상태, 훅 등을 역할별로 구분
- 재사용 가능한 컴포넌트는 공통 폴더로 분리

> 기능 중심 구조를 기반으로 관련 파일을 가까운 위치에 배치하여 탐색성과 유지보수성을 높입니다.

#### 구조 및 설계

- UI와 상태 로직을 분리
- 재사용 가능한 컴포넌트는 공통 컴포넌트로 분리
- 컴포넌트 분리는 재사용성과 가독성을 기준으로 판단
- 컴포넌트는 단일 책임 원칙(SRP)을 따르되, 과도한 분리로 인한 복잡도 증가를 방지하기 위해 적절한 수준에서 설계
- 하나의 컴포넌트는 하나의 역할만 수행하도록 구성

> 단, 재사용 가능성이 낮고 해당 컴포넌트 내부에서만 사용되는 경우에는 과도한 분리를 지양합니다.  
> 이러한 로직은 상위 컴포넌트로 전달하거나 유틸로 추상화하지 않고 내부에서 처리합니다.

#### 상태 관리

- 전역 상태는 Recoil을 사용하여 관리
- 파생 상태는 selector를 통해 계산
- 상태는 필요한 단위로 분리하여 관리하고,  
  selector를 활용해 필요한 값만 계산하여 불필요한 리렌더링을 최소화

#### 스타일링

- Tailwind CSS 기반 스타일링
- 모바일 퍼스트 기준으로 스타일 적용
- 주요 기준 해상도 (viewport width 기준):
  - 320px: 최소 화면에서 레이아웃 깨짐 여부 확인
  - 375px ~ 390px: 기본 디자인 기준
  - 430px: 확장 모바일 화면 확인
- 데스크탑 화면은 `lg` 브레이크포인트부터 대응
- 조건부 클래스:
  - 복잡한 경우 `clsx` 사용
  - 단순한 경우 템플릿 문자열로 처리

#### 성능 및 기타

- 상태 변경 범위를 최소화하여 불필요한 리렌더링을 방지
- UI 컴포넌트에는 비즈니스 로직을 최소화하고, 로직은 훅 또는 상태 관리로 분리
- 불필요한 props 전달을 줄이고 컴포넌트 간 의존성을 최소화

## 5. 주요 기술적 결정

### 5.1 모바일 퍼스트 설계

주요 사용자층의 모바일 사용 비중이 높다는 점을 고려하여 모바일 퍼스트 방식으로 UI를 설계했습니다.

작은 화면(375px 기준)을 기준으로 레이아웃을 먼저 정의하고, 이후 확장하는 방식으로 구성하여  
다양한 화면 크기에서도 일관된 UI를 유지할 수 있도록 했습니다.

또한 최소 해상도(320px)에서도 레이아웃이 깨지지 않도록 검증했으며,  
데스크탑 환경은 `lg` 브레이크포인트를 기준으로 확장할 수 있도록 구조를 구성했습니다.

### 5.2 Recoil 기반 상태 관리 선택

장바구니 및 결제 흐름에서는 여러 페이지 간 공유되는 상태가 존재하므로 전역 상태 관리가 필요했습니다.

또한 본 프로젝트는 별도의 백엔드 API 없이 클라이언트에서 상태를 직접 관리하는 구조로 구현되었기 때문에,  
장바구니 상품, 결제 대상, 카드 정보 등 주요 데이터를 전역 상태로 관리할 필요가 있었습니다.

초기에는 Context API를 기반으로 상태 관리를 구현했으며,  
상태와 dispatch를 분리하여 구조를 개선했습니다.

그러나 Context API는 하나의 value 객체를 기준으로 상태를 전달하기 때문에,  
value 내부의 일부 상태만 변경되더라도 해당 context를 구독하는 모든 컴포넌트가 리렌더링되는 특성이 있습니다.

또한 상태가 증가할수록 Provider 구조가 중첩되고,  
상태 간 의존 관계나 파생 상태를 직접 관리해야 하는 부담이 발생할 수 있다고 판단했습니다.

이에 따라 상태를 더 작은 단위로 분리하고, 필요한 컴포넌트만 구독할 수 있으며  
selector를 통해 파생 상태를 자동으로 계산할 수 있는 Recoil을 도입했습니다.

### 5.3 테스트 점진 도입

장바구니와 같이 상태 변화와 계산 로직이 많은 영역에서  
로직의 정확성과 안정성을 검증하기 위해 테스트를 도입했습니다.

테스트를 작성하는 과정에서 다양한 예외 케이스를 사전에 고려하게 되어,  
구현 단계에서 놓칠 수 있는 조건을 미리 확인할 수 있었습니다.

초기에는 간단한 단위부터 적용해보며 테스트 방식을 익히고,  
이후 상태, 함수, 주요 컴포넌트 단위로 점진적으로 확장해 나갔습니다.

### 5.4 Storybook 도입

UI 컴포넌트를 페이지와 분리하여 독립적으로 개발하고 검증하기 위해 Storybook을 도입했습니다.

컴포넌트 단위로 다양한 상태를 시각적으로 확인할 수 있도록 구성하여,  
공통 컴포넌트의 재사용성을 높이고 UI 변경 시 영향 범위를 빠르게 파악할 수 있도록 했습니다.

또한 컴포넌트를 문서화하고 공유할 수 있어,  
협업 상황에서 UI 기준을 명확하게 전달할 수 있도록 활용 가능성을 고려했습니다.

### 5.5 Vite 기반 개발 환경 선택

React 프로젝트 초기 구성 시 개발 환경 구축 비용과 생산성을 고려하여 Vite를 선택했습니다.

빠른 개발 서버 구동 속도를 제공하고,  
ES Module 기반 개발 서버를 통해 변경 사항을 빠르게 반영할 수 있다는 점에서  
개발 경험을 개선할 수 있다고 판단했습니다.

또한 Vite 환경과의 호환성을 고려하여 Vitest를 테스트 도구로 선택했으며,  
간단한 설정으로 빠르게 테스트를 실행할 수 있어 개발 흐름에 적합하다고 보았습니다.

## 6. 기존 문서 참고 및 관리 가이드

### 6.1 문서 참고 방법

- 요구사항 분석 문서  
  - 기능 정의 및 초기 요구사항을 정리한 문서  
  - (`01.products_requirements.md`, `02.payments_requirements.md` 등)

- 개발 문서  
  - 실제 구현 과정에서의 구조 및 설계 내용을 정리한 문서  
  - (`01.products_docs.md`, `02.payments_docs.md` 등)

- 리뷰 문서  
  - 구현 결과를 기반으로 기능 및 UI를 정리한 문서  
  - (`01.products_review.md`, `02.payments_review.md` 등)

- UI 및 컴포넌트 구조  
  - Storybook을 통해 확인 가능

- 테스트 코드  
  - 테스트 파일을 통해 검증 범위 및 동작 확인 가능

> 필요에 따라 기능별 문서를 함께 참고하면  
> 요구사항 → 구현 → 결과 흐름을 기준으로 프로젝트를 이해할 수 있습니다.

### 6.2 문서 갱신 규칙

문서는 프로젝트 진행에 따라 지속적으로 업데이트됩니다.

- 새로운 기능이 추가될 경우 관련 문서를 함께 업데이트합니다.
- 기존 기능이 변경될 경우 변경된 내용에 맞게 문서를 수정합니다.
- 구조 또는 설계가 변경되는 경우 해당 내용을 문서에 반영합니다.

문서와 실제 코드 간의 일관성을 유지하는 것을 기준으로 관리합니다.
