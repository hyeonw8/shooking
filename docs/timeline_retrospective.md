## 주요 경험 기반 회고

### 1. 상태 관리 구조 개선 (Context API → Recoil 전환)

- 영향:  
  상태 관리 복잡도가 증가하면서 기존 Context 기반 구조의 한계를 인지하고,  
  Recoil을 도입하여 상태 구조를 개선하게 되었습니다.

- 통찰:  
  Context는 value 객체 기반으로 동작하기 때문에 일부 상태 변경에도  
  구독 컴포넌트 전체가 리렌더링될 수 있으며,  
  파생 상태를 직접 계산해야 하는 구조적 부담이 존재한다는 것을 알게 되었습니다.

  이를 통해 상태 관리는 단순 구현이 아니라  
  확장성과 렌더링 영향 범위를 함께 고려해야 한다는 것을 인식하게 되었습니다.

- 액션 플랜:  
  이후 상태 설계 시 atom 단위로 상태를 분리하고,  
  selector 기반으로 파생 상태를 관리하는 구조를 우선적으로 고려하며,  
  상태의 책임 범위를 명확히 나누는 방식으로 설계할 예정입니다.

---

### 2. 테스트 및 Storybook 도입

- 영향:  
  장바구니 기능 구현 과정에서 테스트와 Storybook을 도입하여  
  기능 검증과 UI 구조를 분리하는 개발 방식을 적용하게 되었습니다.

- 통찰:  
  단순 UI 확인만으로는 다양한 상태 변화에 대한 안정성을 보장하기 어렵고,  
  테스트를 통해 예외 케이스를 사전에 검증하는 것이 중요하다는 것을 알게 되었습니다.

  또한 Storybook을 통해 컴포넌트를 독립적으로 관리하면서  
  UI 재사용성과 설계 명확성이 높아진다는 것을 경험했습니다.

- 액션 플랜:  
  이후 프로젝트에서는 테스트를 먼저 작성하는 방식(TDD)을 점진적으로 도입하고,  
  기능 구현과 테스트를 병행하여 안정성을 확보할 예정입니다.  
  또한 주요 UI 컴포넌트는 Storybook으로 관리하여  
  개발 과정에서 발생할 수 있는 변경 영향을 빠르게 확인하고,  
  유지보수성을 지속적으로 확보할 계획입니다.

---

### 3. React / Recoil 호환성 문제 해결

- 영향:  
  Recoil 도입 과정에서 React 19 환경과의 호환성 문제가 발생하여  
  프로젝트 전체 개발 환경을 재정비하게 되었습니다.

- 통찰:  
  라이브러리 선택 시 기능만 고려하는 것이 아니라  
  React 버전, 타입 패키지, 테스트 및 개발 도구와의 호환성까지  
  함께 고려해야 한다는 것을 알게 되었습니다.

- 액션 플랜:  
  이후 새로운 라이브러리를 도입할 때는  
  공식 문서와 호환성 이슈를 사전에 검토하고,  
  프로젝트 환경과의 적합성을 충분히 확인한 후 적용할 예정입니다.

 ## 프로젝트를 통해 배운 점

이번 프로젝트를 통해 단순히 기능을 구현하는 것뿐만 아니라  
상태 관리 구조, 테스트 도입, 개발 환경 구성까지  
전체적인 개발 흐름을 고려하는 것이 중요하다는 것을 배울 수 있었습니다.

특히 상태 관리에서는 단순 구현이 아닌 확장성과 렌더링 영향 범위를 고려해야 한다는 점을 알게 되었고,  
테스트와 Storybook을 통해 기능과 UI를 분리하여 검증하는 방식의 중요성을 경험했습니다.

라이브러리를 도입할 때는 기능뿐만 아니라  
React 버전 및 개발 도구와의 호환성까지 함께 고려해야 한다는 점을 배웠습니다.

프로젝트를 진행하며 문서화의 중요성도 직접 체감할 수 있었습니다.  
단순 기록이 아니라 목적에 맞는 구조로 내용을 정리하는 것이  
개발 과정과 결과를 명확하게 이해하는 데 도움이 된다는 것을 느꼈습니다.

또한, 테스트를 직접 도입하고 작성해보면서  
단위 테스트뿐 아니라 사용자 흐름을 검증하는 통합적인 테스트의 필요성을 이해하게 되었고,  
실제 서비스에서는 테스트가 안정성을 확보하는 중요한 역할을 한다는 점을 알게 되었습니다.

주어진 과업 외에도 개발을 진행하며  
스스로 불편한 점을 인지하고 개선 방향을 고민하는 경험을 할 수 있었습니다.
단순히 기능을 구현하는 데 그치지 않고  
사용하면서 불편한 부분을 직접 발견하고 개선 방향을 고민하는 과정이  
개발 역량을 높이는 핵심 요소라는 것을 체감했습니다.

마지막으로 모든 기능 구현 과정에서  
실무에서는 어떤 기준과 구조로 문제를 해결하는지를 고려하며  
실무에 가까운 구조로 설계하려고 노력했습니다.

## 향후 개선 방향

Recoil을 통해 atom 기반 상태 관리의 장점을 경험하면서  
Jotai, Zustand와 같은 다른 상태 관리 라이브러리도 적용해보고  
각 도구의 특징을 비교하며 상황에 맞는 선택 기준을 정립해보고자 합니다.

현재 Mock 데이터 기반으로 구현된 구조를 넘어  
실제 API 연동 환경에서도 확장 가능한 구조로 개선하고,  
결제 흐름을 보다 현실적인 서비스 수준으로 발전시키고자 합니다.

테스트는 현재 일부 영역에만 적용되어 있기 때문에  
결제 흐름과 주요 사용자 시나리오까지 확장하여  
기능 변경에도 안정적으로 유지될 수 있는 구조를 구축할 예정입니다.

더 나아가 상태의 책임 범위를 명확히 분리하고  
UI 상태와 비즈니스 상태를 구분하는 구조로 개선하여  
코드의 가독성과 재사용성을 높이고자 합니다.

사용자 흐름을 기준으로 상태를 설계하여  
사용자 행동에 자연스럽게 반응하는 UI를 구현하고,  
보다 나은 사용자 경험(UX)을 제공하는 방향으로 개선해 나갈 계획입니다.
